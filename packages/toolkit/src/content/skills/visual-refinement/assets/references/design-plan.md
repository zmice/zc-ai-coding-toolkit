# 从方向到页面蓝图与执行计划

本仓库在 Unslop 方向与九轮方法上的扩展。上游作者、固定版本与 CC BY 4.0 声明见 [LICENSE-unslop.txt](LICENSE-unslop.txt)。用于 `new/heavy` 的规划、实现和验收；`light` 只保留相关项。

## 生命周期交接

本节是页面设计判型与阶段交接的共享契约。`command:start` 保留轻量分流，阶段入口只保留直接进入时的兜底，不各自扩写另一套规则。无需用户点名 Unslop，也不新增 workflow。

| 任务证据 | 处理 |
| --- | --- |
| 新页缺少结构/视觉设计，或已有页需整体重塑 | 目标明确后进入本流程；目标不明先收敛业务 |
| 已有可执行方向、蓝图或计划 | 从未完成项续接，复用 owner 和 ID，仅补缺口 |
| 局部功能/样式修复、纯审查、非前端任务 | 沿原路线；前端修复交前端工程，纯 UI 审查交 UI/UX review，不强加全面设计 |
| 只要方案 | 采用必要设计步骤，在响应中交付，不写计划文件或产品代码 |

直接进入 spec/plan/build 且未经过 start 时，也按上述判型处理。专项技能不可用时说明缺口，按现有本地契约继续可做部分，不宣称已调用。已授权实现不因采用设计能力或阶段切换重复索取批准。

方向、区域蓝图、组件 owner、计划 ID、待定项和验收组成一个交接包，写入已有 spec/plan 或只读响应，不额外创建第二套计划。Spec 收敛任务与蓝图，Plan 将区域决定映射到实施 ID，Build 按 ID 实现并记偏差，Review 核对蓝图符合程度，Verify 将真实渲染与交互证据回填同一 ID。用户从中途续接时只处理未完成项，不重启整个设计流程；设计偏差有证据才更新原决定。

技能路由是代理执行约定，不是 CLI 自动状态机；工具不可用或无法取得画面时如实记录缺口。只给方案的边界在所有阶段持续有效，已授权实现也不因阶段切换重复请求批准。

## 1. 把方向变成可判断的选择

先读 `skill:frontend-ui-engineering` 的本地设计契约；沿真实渲染路径确认 token、组件、数据、URL 和 overlay owner。尚未定位的 owner 写“待查”，不能编造文件名。

方向每项都写 **业务依据 → 页面选择 → 可检查结果**。例如仓库异常处理页的“紧凑、明确”可以对应：待处理队列成为主要区域、严重程度用已有语义标签表达、分派操作在行内或既有 Drawer 可达。不能只写“高级、现代、精致”然后任意换皮。

- Product 决定主要任务、信息顺序与操作；Character 决定密度、排版与反馈节奏。
- World 提供内容和材料的依据，不要求给后台铺满装饰背景。
- Moments 选择需要强调的业务内容；Signature 复用一个有意义的细节，无合适候选可保留现状，不制造装饰。
- 有明确方向就选定并继续；只有真实取舍无法由现有证据解决时才比较备选，不强制生成三套设计或逐轮索取批准。

## 2. 页面蓝图

在现有设计文档或响应里用短表/线框说明以下内容。仅有“更好层级、优化留白”不构成蓝图；无需为每次精修新建文档。

已知目标与组件足够时就给暂定蓝图，不把所有设计选择推迟到后续动作中。例如内容发布页可暂定：宽屏顶部是标题、草稿状态与发布操作，主体编辑器与预览并排；窄屏按标题/状态 → 编辑器 → 预览阅读，发布操作仍可达。需要查源码的是具体 API、断点、路径和权限，不是虚构它们已确认。示例只说明交接粒度，实际布局须服从当前产品任务。

| 区域 | 用户任务与真实内容 | 宽屏位置/优先级 | 窄屏顺序/溢出策略 | 组件与状态 owner |
| --- | --- | --- | --- | --- |
| 具体区域名称 | 主要操作、字段来源、事实或待确认假设 | 谁先被看见，哪些内容可以压缩 | 折叠、滚动、换行及操作可达性 | 已定位的组件、数据、URL/overlay owner |

补充必要的状态差异：加载、空、错误、禁用、成功、权限、焦点；长中文、长数字、密集数据下的行为。以核心任务决定页面类型：后台强调查找和操作，内容页强调阅读，营销页强调可信主张与行动，不把一个 hero 配方套给所有页面。

操作型页面在约定的宽窄屏首屏中让用户能开始主要任务，例如看到搜索或首个输入。检查大标题、重复说明、装饰区是否把操作挤出首屏；优先调整结构和删减重复说明，不以缩小文字替代。长表单不要求所有字段和提交按钮同屏；确需前置说明时给出业务依据。验收记录实际位置与画面，不能只检查“无横向溢出”。

已有页默认保留业务功能、内容事实和区段顺序。用户授权结构优化或新证据表明必须重排时，逐项说明依据、位置变化和入口保留；用户明确限制不可重排时遵守限制。不能以视觉简洁为由删除字段、改权限或隐藏必要操作。新页确认必要内容与主任务，演示数据明确标注，不能编造用户数、收益、实时状态。

多页任务先固定共享 token、导航、状态和复用组件，再写每页不同的主要任务与蓝图；不顺手改未纳入范围的页面。

只说“列表用于查找、详情用于跟进”仍不够：分别给出区域顺序和主操作位置，并说明哪项共享契约先确定、哪些页面实现随后可以独立推进。

## 3. 执行计划与推进

规划是实现的输入。已有实现授权时，在形成足够具体的第一切片后直接开始，不要求用户重复确认；只给方案时保持只读，包括不写计划文件。

多页只读方案也必须列后续代码实现的切片，而非只有调研和写方案步骤。每页至少一项说明区域/组件职责、依赖及“操作 → 预期结果”；共享规则先确定，不相互依赖的页面可在其后独立实施。路径、字段或 API 未查明就标为待查，不妨碍根据已知业务给出暂定验收。方案里的实现状态均为待执行，不能为了完成这些条目而越界改代码。

| ID | 依据与设计决定 | 目标区域/owner | 实施动作与依赖 | 可观察验收 | 实现/验证状态与证据 |
| --- | --- | --- | --- | --- | --- |
| U1 | 对应任务、方向或问题证据 | 实际文件/组件，未查明则待查 | 具体改动；依赖哪项/哪个输入 | 用户能看见或完成什么、如何检查 | 待实现 / 已实现；待验证 / 通过 / 失败 / 阻塞；证据位置 |

首轮计划可缩成 2–3 项。例如 U1 核对数据/权限与已有组件（产物为字段和 owner 映射）；U2 依赖 U1，落实编辑器和预览（验收输入与预览一致，宽窄屏均可编辑）；U3 依赖 U2，接入发布及反馈（验收成功、失败、无权限和焦点恢复）。不能用“稍后建立可执行计划”代替这些已能确定的动作，也不能把暂定计划写成已实施。

- `new/heavy` 先确认内容和结构，打通主任务，再做间距、色彩、排版等细化。避免先抛光即将被替换的布局。
- 复用项目组件和 token。新增变体须说明为何现有能力不足；视觉改造不复制组件、不绕过数据/权限 owner。
- 按依赖实现；九轮检查是发现遗漏的视角，具体变更挂回计划 ID，允许一项同时解决多轮问题。
- 发现设计与渲染冲突时记录“原决定 → 新证据 → 调整 → 受影响验收”，更新计划后继续授权范围内工作。涉及新增业务或超出授权的改动单独列出。
- 缺少参考画面只阻塞依赖它的选择；继续查本地契约、内容和组件。忠实匹配所需证据必须明确索取，不能靠假设宣称匹配。

## 4. 计划到渲染的验收

逐项回答：方向落实在哪个区域？真实渲染是否符合蓝图？主要操作是否可达？宽窄屏、状态、长文本与键盘路径是否成立？用实际证据更新每个 ID，不用“九轮完成”代替结果。

已有页使用同条件前后证据；新页比对 brief 和蓝图，不索取旧截图、不伪造 before。真实浏览器交互与自动检查分别记录。工具缺失、页面未启动或依赖未就绪时保留“待验证/阻塞”，说明原因与下一验证动作；不能把静态代码审查、示意图、story 或截图数量当作产品验收。
