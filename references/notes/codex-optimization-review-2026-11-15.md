## 官方建议与采用边界

1. **角色权限继承父会话。** 最新文档说明，custom agent 中的 `sandbox_mode`、`approval_policy`、`model_provider`、`mcp_servers` 不覆盖父配置；写“只读”也不会创建独立只读沙箱。支持的能力收窄字段与 `skills.config` 应按宿主版本验证后使用。[官方子智能体文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)
2. **技能按需加载。** 名称与描述帮助选择技能，正文在使用时加载。应优化触发条件、附件拆分和选择质量，不应把所有文件大小当成每轮上下文消耗。[官方技能说明](https://developers.openai.com/plugins/concepts/skills)
3. **插件可逐步迁移格式。** 官方推荐根 `plugin.json` 的 portable 格式，同时保留 `.codex-plugin/plugin.json` 兼容回退。当前双清单可选生成已有价值，暂不直接切换默认格式。[官方插件打包说明](https://developers.openai.com/plugins/build/plugins)
4. **升级应跟随能力验证。** 0.169.0 包含项目 trust、Windows 沙箱及 MCP 等待等修复，但尚不能证明能解决本项目既往的全部评测阻塞。[官方更新日志](https://learn.chatgpt.com/docs/changelog)

## 第一批：可靠性与真实状态（P1）

### C01：缩小升级前查询范围——已确认实现问题

- 证据：`apps/cli/src/cli/platform.ts:1864,1935` 在升级前执行全量 `codex plugin list --available --json`；同会话此前已观察到本机被该阶段拖住。后续查询已有 marketplace 作用域。
- 影响：升级 zc-toolkit 依赖其他插件来源的响应，操作范围过大。
- 建议：查询目标插件的安装/启用状态和目标 marketplace。启用状态不明确时返回可解释的 unknown，不能默认重新启用。
- 验收：无关 marketplace 挂起不阻塞目标升级；目标缺失、已禁用、查询失败分别得到正确结果；保留用户禁用状态。修改固化旧命令的测试。

### C02：给 Codex 子进程设置边界——已确认实现缺口

- 证据：`apps/cli/src/cli/platform.ts:1556` 的命令执行缺少 deadline、输出大小上限及超时后的受控子进程树清理。
- 影响：查询挂起可无限等待，持续输出可持续占用内存。
- 建议：查询/安装/升级采用分级超时和输出预算；失败包含阶段、退出状态和截断信息；仅清理本次拥有的进程树。
- 验收：挂起、输出洪泛、取消、启动失败均可终止并得到机器可读结果，不影响用户其他 Codex 会话；Windows/Linux 分别验证。

### C03：精确插件身份和状态语义——已确认实现问题

- 证据：`platform.ts:1715` 允许仅凭同名匹配首条插件记录；`:2499` 的 overall complete 主要依据 installed/enabled 与 companion 文件状态，未覆盖 pending update。
- 影响：同名不同 marketplace 可误匹配；安装健康、版本最新和当前会话生效容易混淆。
- 建议：优先完整 plugin ID，重复结果返回 ambiguous；分别保留 installed/enabled、available version、update pending、companion current、runtime verified。查询不到最新版本时保留 unknown，不能自动断言成功或失败。
- 验收：同名来源、多条记录、缺失版本、待应用更新、旧会话缓存都有独立测试；unknown 不伪装成 latest，静态 complete 不伪装成运行时验收。

### C04：完整回滚 companion 文件——已确认事务范围缺口

- 证据：`platform.ts:2555` 的事务只包围配置文件及 receipt 快照，内部还会写多个 agent 文件；`apps/cli/src/utils/codex-agent-config-transaction.ts:43` 明确该范围。
- 影响：中途失败可能留下新角色文件、旧配置或旧回执；当前返回 partial，不等于状态已恢复。
- 建议：将本次所有受管文件纳入阶段化写入/备份恢复；同时处理本次新建文件与既有文件。插件升级与 companion 同步不是同一原子事务，应分别报告可恢复边界。
- 验收：在第 N 个 artifact 写入、配置合并及 receipt 落盘失败处注入故障；对比所有文件与回执、验证重试幂等，保留非受管文件。

### C05：修正权限承诺和文档漂移——已确认文档问题，运行时能力待验证

- 证据：`docs/architecture/codex-multi-agent-controller.md:71,83,96` 的权限、顶层配置所有权及模型表落后；`docs/architecture/platform-capability-matrix.md:38,201` 仍有旧能力描述/九角色数量。当前实际为十角色。
- 建议：区分“指令要求只读”和“宿主强制只读”；MCP 在父会话配置。由 canonical 元数据生成角色/模型/权限说明表或增加一致性检查。已有 `sandbox_mode` 字段如何兼容旧宿主，先查证再迁移，不能直接认为字段已提供隔离。
- 验收：文档不再承诺 child 自设沙箱或 MCP；隔离案例记录父权限及子任务实际可用工具。只读安全要求由有效宿主边界保证；缺乏证据时明确能力未验证。

## 第二批：角色、技能与执行质量（P2，随运行时验收推进）

### C06：模型策略和顶层配置所有权——设计优化

- 初次审阅时，十个角色均硬固定模型和 effort；生成器还给普通子任务提供顶层固定默认值。角色 hard pin 优先，修改顶层默认不会改变这些角色。后续源码修正见 C06 实施进展。
- **已有保护必须保留：** CLI 仅补缺失默认值、更新仍匹配回执的受管值，保留用户已有或自行修改的值。这里不是“无条件覆盖用户配置”的缺陷。
- 建议：显式区分角色模型策略与全局子任务默认策略。默认安装只管理 zc 角色；全局默认由显式选项管理。旧受管值迁移须依照回执，不静默删除。模型选择可表达继承或固定，仅在任务质量/成本评测证明有收益时调整角色。
- 验收：用户值保留、旧回执升级、卸载、继承与固定四类行为均有测试；用真实子任务记录核对有效模型/effort，不以 TOML 内容代替结果。不要直接全量升级模型或增加新角色。

### C07：把依赖声明与可执行约束分开——契约澄清与补强

- `requires`、`tools` 已有 schema，但 Codex TOML 生成主要采用角色正文及 `codexAgent`。它们不自动加载技能，也不形成工具白名单。
- 建议：明确治理字段语义；必要技能在角色正文中给出调用条件和缺失时降级。仅将官方支持且验证过的能力开关映射为宿主配置，不能把抽象工具名直接当安全权限。
- Markdown agent 与 companion TOML 来自同一内容源，但后者带模型配置；分别核对发现名称、入口用途和有效指令，避免歧义。在验证替代机制前保留 companion。
- 验收：生成测试验证依赖指引；真实 reviewer/frontend 子任务有技能读取/使用证据；两个入口的配置差异被记录，而不是默认视为等价。

### C08：减少技能误触发与目录竞争——设计优化

- 72 个入口中包含短命令别名与完整技能。无静态前缀冲突不等于没有语义重叠；本会话还有其他官方插件一起参与选择。
- 建议：优先调整 description 的正反触发条件，保留渐进式附件加载。对纯手动别名试验 `agents/openai.yaml` 的 invocation policy，再决定是否推广；禁止隐式调用不等于从目录移除，也不保证减少 token。
- `start`、前端设计与 `visual-refinement` 应继续支持自然语言触发。不要为了减少入口数破坏用户命令名。
- 验收：在实际宿主下检查发现是否完整、描述是否截断；合成题覆盖该调用/不该调用/明确点名三类；比较任务效果、调用次数、延迟和实际用量。当前未设预算的静态审计只能作基线。
- 官方依据：[技能构建与 invocation policy](https://learn.chatgpt.com/docs/build-skills)、[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

### C09：收敛多 agent 调度契约——设计优化

- 保留现有 `agent_opportunity.dispatch_now`、文件所有权、loop budget、checkpoint 和 fan-in；不另建并行控制器。
- 改进方向：只有可独立产出、足以抵消协调成本的任务才派发；简单问题主线程处理；已有 agent 用于相关追问；同文件写入不并发。审查角色不要因“任何改动”无差别全量启动。
- 并发数以当前宿主实际容量为准。官方配置上限不含主线程，本会话工具槽位总数含主线程，需归一化后计算；不要直接硬编码为同一个数字。
- 验收：无多余派发、无重复调查、无所有权冲突；失败/超时能收敛；平台没有 close 工具时不虚构生命周期操作。

### C10：补齐 Unslop 的 Codex 行为验收——保留实现，验证可靠性

- 已有链路：`commands/start/body.md:47,52` 自动接视觉规划；`skills/frontend-ui-engineering/body.md:15` 也会按新页/整页重塑条件接 `visual-refinement`。frontend agent 虽没有直接写该技能名，但通过前端工程技能已有路径，不能据此判定功能缺失。
- 建议：保持同一设计蓝图、计划 ID、实现和验收映射，重点测试自然语言触发及子 agent 交接；识别 Figma、浏览器、截图等实际可用能力并复用现有项目设计系统。
- 验收至少四例：新页设计、已有页重塑、已有明确设计稿、单点样式修复。前两类完整走设计链；后两类不无条件扩大改造。只要方案保持只读，授权实现继续到真实浏览器。已有页保留同条件前后证据。
- 现有安装脚本只检查八个关键技能被发现；不能证明设计实际执行，历史未完成的模型评测不能算全部通过。

## 第三批：版本兼容、发布与长期维护（P2）

### C11：建立真实宿主兼容表，再升级 CLI / portable 格式

- 当前能力探测主要看子命令 `--help` 成功，不足以证明具体 flags 或角色字段可用。
- 建议：记录 CLI/桌面宿主版本、命令参数、清单格式、角色发现、能力开关和 app-server 方法支持情况。以隔离 home 测试当前 0.167 和候选 0.169；桌面能力单独验收，不能用外部 CLI 版本替代。
- portable 输出已有 CLI 0.167 安装/发现证据，默认兼容清单继续保留。新字段通过解析和行为验证后再加入 schema，未知能力应降级并说明。
- 0.169 的 project trust 变更需加入测试；不要为了让测试通过而自动信任任意项目。升级本地/服务器时保存 launcher、安装方式和代理环境，验证新进程，避免重演代理 wrapper 被替换的问题。
- 验收：Windows/Linux、当前/候选 CLI 为核心矩阵；桌面 fresh session 验证入口发现；旧清单/portable 均不产生重复技能或陈旧清单优先级问题。

### C12：从分发验证提升到运行时证据——现有框架上补强

- 已有 `scripts/skill-distribution-audit.mjs` 明确不证明模型加载；`scripts/verify-codex-design-install.mjs` 证明指定技能发现；`scripts/lib/codex-eval-capture.mjs` 可用于真实线程证据。应连接这些能力，不重复建设。
- 建议输出四层结果：产物/来源一致；宿主发现与启用；角色实际模型/权限/技能；任务结果及必要浏览器证据。未知/失败/未执行必须分开。
- 用冻结输入、独立 oracle 和相同任务做 before/after；记录实际子任务，不把模拟 transcript 当原生调度。仅使用已获授权的技能与合成题，不扩大源码或私人配置出站范围。
- 验收：相关包测试、`pnpm verify`、`pnpm release:check` 之外，提供两宿主的新会话证据；Windows 运行阻塞时标为 inconclusive，修复并重跑后才宣称对应能力通过。

### C13：按需吸收 MCP / hooks 能力——条件性扩展，暂不默认引入

- 当前插件的核心价值是工作流、技能和角色，官方允许纯指令技能插件，不要求自建 MCP 服务。
- 建议：只有出现明确、重复且可可靠执行的动作才考虑 hook 或工具，例如确定性的验证入口。复用已有官方工具发现；MCP 连接在父会话管理。
- 官方打包文档对 lifecycle hooks 的支持场景有限定，不能等同于所有 CLI、市场安装或角色钩子都可用。
- 验收：目标宿主支持、超时/重入/失败降级、权限与日志脱敏均清楚；没有明确收益就继续使用当前技能编排。不要新增默认后台进程或扩大权限来缓解允许框问题。

## 建议执行顺序与完成条件

1. **可靠性补丁：C01–C05。** 修复升级查询、子进程边界、状态匹配和 companion 回滚；同步确定有误的文档。优先消除已观察到的阻塞和错误承诺。
2. **兼容性与运行时基线：C11–C12。** 建立最小宿主矩阵，在有效支持范围内安排 CLI 升级。获得有效配置和实际行为证据后，再决定更改角色 schema。
3. **执行质量优化：C06–C10。** 小批调整模型策略、依赖、触发和调度；每批有 before/after 案例，保留用户已有命令和设计流程。
4. **按需扩展：C13。** 仅依据具体需求开展，未验证能力不进入默认发行配置。

改动责任边界：CLI 生命周期在 `apps/cli`；Codex 序列化在 `packages/platform-codex`；内容与元数据在 `packages/toolkit/src/content`；跨平台 schema 变更必须确认其他适配器不受影响。生成目录、已安装插件缓存及用户配置不作为源码修复入口。

发布完成条件：针对性回归、全量门禁、隔离安装/升级/回退、原生角色/技能行为检查、前端案例真实浏览器验收均有对应证据；最后再核对本地和开发服务器实际安装及新会话。通过静态检查或版本一致不能替代这些验收。
